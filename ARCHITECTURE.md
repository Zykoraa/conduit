# Conduit 2.4.3 architecture and release process

## Connection notifications

`TrayNotificationPolicy` announces the first verified result in each connected lifecycle phase. Losing verification while the controller remains Connected does not reset that announcement. Entering Connecting, Disconnected or Faulted permits a new announcement after verification succeeds. This prevents a temporary UDP check failure and recovery from producing repeated Windows connection alerts, while dashboard health and fault alerts retain their actual state. Behavioral checks cover these sequences, and the published app and installer exercise the same policy after obfuscation.

## Release obfuscation

`build/Obfuscation.targets` uses the SDK's `PrepareForBundle` / `FilesToBundle` extension point. It obfuscates a separate copy of our managed assembly, then replaces that one bundle input. It never mutates the compiler output, NuGet cache, QRCoder, runtime assemblies, or pinned engines. App and installer use the same policy. Packaging forces obfuscation and fails if the tool, coverage check, or published-executable checks fail; there is no unobfuscated fallback.

`dotnet-tools.json` pins Obfuscar 2.2.50. Implementation types, methods and fields are renamed and method strings are hidden. Properties, events, constructor parameter names and enums retain their contracts for JSON, data binding, diagnostics and IPC. Generated Windows interop is excluded. Native import entry points remain intact. Changing these exclusions requires testing saved data and cross-process compatibility again.

`ReleaseSmokeChecks` runs inside the finished single-file executable via `--release-smoke-test <report-path>`. It verifies renaming, profile/import serialization, nested broker contracts, framed in-memory IPC, update/rollback/incident/history JSON, anonymous and Owner response contracts, DPAPI, icons, absence of the retired map resource, and construction/rendering of every dashboard page. The installer also verifies its embedded signed payload. This mode starts no engines, makes no network requests, installs nothing, and changes no preferences; it writes only the requested report. It is a packaging check, not a replacement for the behavioral or native integration suites.

Reverse maps are archived privately under `artifacts/private/obfuscation/<version>/<flavor>/<assembly>-<SHA256>/Mapping.xml`, outside the publish directory and Git. Distribution checks reject maps, source files and debug symbols. Signatures and package hashes are calculated after obfuscation. Preserve private maps for decoding support traces, but never distribute them. Obfuscation is reversible; credential protection and the elevated-host trust boundary remain independent requirements.

## Process and trust boundaries

The WinForms dashboard runs as the interactive user. A UAC-approved instance of the installed executable, `--tunnel-host`, owns Xray and sing-box. It must run from the protected Program Files installation. Its named pipe permits the same Windows SID and rejects network identities; the server impersonates each caller to check the SID. The client verifies the pipe server's executable path before sending a profile. Messages are length-bounded and commands form a fixed allowlist. No shell command, arbitrary executable path, or arbitrary configuration document is accepted over this pipe.

The host and engine children share a Windows job with kill-on-close. Closing the dashboard does not terminate that job; host termination does. Only one host is allowed across installations and Windows users, because routing and the optional WFP lock affect the whole machine. The host is an on-demand elevated process, not an always-installed Windows service. It does not automatically connect at boot. UAC approval with a different administrator account is not supported in this release.

App binaries, engine binaries and templates live under Program Files. Elevated update staging and rollback files live under ProgramData with user read-only access. The host's runtime folder is restricted to the caller and administrators. User profile saves use current-user DPAPI; engine processes temporarily need readable generated configuration files. A normal disconnect deletes those files. A crash can leave them in the restricted runtime folder. Old 1.x files, exported links, page files and OS backups are outside the migration's cleanup scope. DPAPI does not defend against malware already running as that user or an administrator.

The host exposes observed lock state separately from the selected preference. A read-only WFP transaction checks the persistent sublayer and both stable IPv4/IPv6 block IDs, their layers, action, weight and lack of conditions. A sublayer alone is insufficient. Unknown read results remain unconfirmed. Missing required blocks trigger transactional reapplication during verification; unsuccessful repair faults the tunnel without deleting retained filters. This validates Conduit's required blocks, not every exception or third-party policy on the machine. Conduit never disables Windows Firewall or deletes another application's policies. See SETUP.md for exceptions and recovery. The lock is opt-in, machine-wide, and not a boot-time or anti-malware isolation guarantee.

## Release authentication

`UpdateFeedCodec` verifies an ECDSA envelope using the existing release key. The signed schema binds stable channel, flavor, three-part version, exact versioned asset name, byte size, SHA-256, publication/expiry and key fingerprint. Duplicate, missing or unknown fields are rejected. Feeds expire (packaging signs 30 days; the client permits at most 90), allow five minutes of forward clock tolerance and reject versions below the highest previously verified feed version. The version record is user-local and is not an anti-malware trust boundary. Offline/manual bundle installation remains available.

`UpdateDiscovery` requests direct HTTPS responses without redirects, proxies or cookies. Metadata is limited to 16 KiB. Bundles are streamed with a 300 MB signed size limit, exact final length/hash, cancellation, five-minute download timeout and partial-file cleanup. Requests for a desired connection require fresh verification and bind through `TunnelTransport`; state changes abort them. Disconnected direct requests require manual user action. Automatic discovery is opt-in metadata only, at most every 12 hours through a verified tunnel, with one-hour error backoff. The default points to the official public feed; automatic checks are off until enabled. Existing custom or cleared feed settings remain as saved.

Packaging writes `Conduit-<flavor>-stable.json` and `Conduit-<flavor>-<version>.wtupdate`. Host those files in the same HTTPS directory, with direct 200 responses and no content encoding. Feed assets are relative to their configured origin, so signing does not require choosing hosting first. Renew metadata with `dotnet run --project tools/ReleaseTool/ReleaseTool.csproj -c Release -- feed <versioned.wtupdate> <feed.json>` if validity expires. Hosting/publishing is separate from packaging. Initial Setup trust and elevated re-verification still apply.

`ReleaseTrust.cs` contains only a P-256 public key. The private key is stored outside Git at `%LOCALAPPDATA%\WorkTunnelSigning\release-key.dpapi`, protected for the maintainer's Windows user. The signing tool refuses to sign if its key does not match the embedded public key. Do not put the protected key or a plaintext export into Git, release assets, a coworker package or CI.

A `.wtupdate` holds exactly `package.zip`, `release.json` and `release.sig`. Metadata binds version, Owner/Client flavor, SHA-256 of the package and public-key fingerprint. ECDSA/SHA-256 uses a 64-byte P1363 signature. Both the dashboard and elevated installer independently verify the signature. The elevated installer reconstructs its own plan and hashes in protected staging; it does not trust a dashboard-supplied file list, destination or hashes. Paths reject traversal and linked directories. Device identity files are excluded. File replacement creates a rollback snapshot, and ordinary copy failures restore already-replaced files. Power-loss transaction recovery and automatic rollback based on post-update network behavior are not implemented.

The initial Setup executable has no Authenticode certificate. Obtain Setup from the official public release and compare its published SHA-256 before the initial installation. Signed updates do not remove Windows SmartScreen/unknown-publisher warnings. Signing-key loss requires a new manually trusted installation or a key-rotation release signed by the old key; do not silently generate a new production key. Keep a tested Windows/account backup that can recover the DPAPI key before relying on this machine as the only signer.

## Build and release

1. Run `dotnet run --project tests/WorkTunnel.Checks.csproj -c Release`.
2. Run `scripts/check-engines.ps1`; it checks versions and hashes of every bundled engine file.
3. Build both packages using `scripts/package-owner.ps1` and `scripts/package-client.ps1`. Both are blank-identity installers. Packaging checks the obfuscated executable and enforces a 64 MiB private-memory ceiling over three fresh offline startup/UI runs, using `scripts/check-release-resources.ps1`. Reports stay under ignored `artifacts/private/resources/`. This is a defined regression budget, not a total tunnel-resource limit. The internal ZIPs in `dist` are build intermediates; distribute Setup, `.wtupdate` and signed feed files.
4. Wait for the repository's **Windows release checks** on the exact release commit. It uses a fresh Windows Server runner to exercise real WFP/TUN behavior, job cleanup, installation, deliberately damaged-file repair, host reattachment and uninstall. CI creates an ephemeral signing key on that runner; it never receives the production key.
5. Inspect the actual UI at ordinary/large text sizes and on a small display. Run the final packages' configuration checks. Record test limitations in the release notes.
6. Check the public-source privacy gate and secret scan, tag the tested commit, and upload the blank Owner/Client Setup files, signed updates and SHA256SUMS.txt. Keep an earlier release available. Do not install over an active call.

## Public release hosting

`scripts/prepare-public-release.ps1` independently verifies each production feed signature and its exact version, flavor, asset hash, size and expiry. It copies an explicit allowlist of two Setup files, two versioned bundles, two feeds and checksums into a publication folder. The generated site and pinned Pages workflow live in `distribution/pages`. Publication never copies the application source, private maps, signing key, profiles or diagnostic reports.

The public `Zykoraa/conduit` repository contains a sanitized source snapshot, site template and GitHub release assets. Its history starts with this snapshot; older private history is not copied. Its Pages workflow downloads only the release allowlist, verifies checksums, enforces a 900 MB deployment budget and publishes direct HTTPS files. The app embeds the official per-flavor feed address but leaves automatic checking off. Custom and explicitly cleared feed preferences remain intact. The production signing key stays Windows-protected on the publisher PC; GitHub Actions never receives it. CI package checks and performance runs use ephemeral runner-only trust.

Feeds expire thirty days after signing. Before expiry, run `ReleaseTool feed` for the unchanged versioned bundles using the original protected key, replace only the matching signed feed release assets, and dispatch the public Pages workflow for that tag. A source-control credential cannot create a valid differently signed feed. Metadata expiry stops discovery from that feed without disabling the installed tunnel. Versioned releases remain available in GitHub release history.

`scripts/publish-public-release.ps1 -NotesFile <file>` prepares, verifies and publishes a new version to the dedicated authorized distribution repository. It refuses replacement of an existing release. For unchanged bundles, `-RefreshFeeds` renews only signed metadata and checksums and dispatches Pages again. A publication failure requires inspection before retry; the script does not blindly replace application bytes.

## Resource and transport measurements

`scripts/measure-installed-resources.ps1 -Report <file> -Seconds 600` observes an already running installed edition without starting engines, changing routes or generating traffic. It records private memory, working set, elapsed CPU, process changes and verification across samples. Its results describe the current PC's traffic and window state, rather than a controlled workload. Private committed memory and working set are reported separately.

The manual `benchmark.yml` workflow installs an actual Client package on a disposable Windows runner and downloads TunMon's current publisher-signed executable. It verifies the signed public release manifest and exact executable size/hash before launch. `scripts/run-comparison.ps1` runs both apps with identical pinned engine bytes, a plain local VLESS relay and a verified 1 MiB payload. Both use gVisor and MTU 1400; TunMon imports an aligned benchmark configuration rather than its default routing. Required interface names/prefixes and local API settings differ. Blocking is off in both. The app source is not changed for the measurement.

Two rounds reverse product order. Each run includes thirty seconds of warmup, shown and minimized idle phases, an uncapped local transfer, a sustained 2 MiB/s workload and idle after load. `tools/BenchmarkDriver` verifies every completed payload hash and reports failures. App/host and engine memory/CPU are recorded separately; fixture-server, relay and workload-driver resources are excluded from product totals. Startup means time to the first verified fixture payload, not time to verified privacy. Windows foreground-focus results and final health facts are retained with the measurements.

Conduit's sustained fixture fails if app plus host exceeds 128 MiB private memory, grows by more than 64 MiB during the load phase, fails to sustain 1.8 MiB/s of the 2 MiB/s target, or averages over 15% of one CPU core during an idle phase. These thresholds apply only to the documented CI scenario. The existing offline package memory gate remains separate. Reports record hardware, OS, engine pins, versions, workload and limits; partial runs cannot pass. Local HTTP throughput is not WAN or TLS capacity. This comparison does not establish battery efficiency, day-long stability, roaming behavior or an overall security ranking.

## Maintaining engines

Pinned engines are a tested pair, not a promise to freeze them forever. `engines.lock.json` records upstream repositories, versions and file hashes. `scripts/evaluate-engine.ps1 -Engine xray -Tag <official-tag>` (or `sing-box`) downloads a Windows x64 candidate from its official GitHub repository, requires its published SHA-256 digest, verifies that digest before executing anything, then validates the current configuration. It writes only a separate candidate folder and does not update the app.

Before adopting a candidate, review upstream release notes, security advisories, licenses and configuration migrations. On a branch, replace the candidate engine files, intentionally update the lockfile, and run the behavioral and native Windows tests. Test real DNS, HTTPS, Discord voice/video, reconnect and wake on representative networks before shipping the engines together. A candidate passing configuration syntax alone is not release approval. Engine-only silent updates are not supported.

## Validation limits

The controller's platform seam simulates DNS failure, engine startup failure, wake, interrupted connection and late probe completion without modifying host routes. Native tests use the real bundled sing-box TUN and a controlled SOCKS responder. A second non-exempt interface provides reachable IPv6 documentation addresses: actual TCP/UDP packets must pass before filtering, fail while blocked, and pass after explicit recovery. Missing IPv6-filter removal/repair, selected-TUN exceptions, applying-process exit and TUN crash are tested against that live fixture. The test waits for IPv6 duplicate-address detection to finish before establishing its baseline. An additional IPv6 internet check runs only when the runner has that connectivity; the fixture is required either way. GitHub's Windows runner does not substitute for a Windows 11 laptop, roaming radio, sleep/resume or Discord soak test. Accessibility metadata and keyboard/layout checks supplement visual inspection; full assistive-technology certification is not claimed.

## Product name and compatibility

Conduit (formerly WorkTunnel) uses the tagline **Connected on your terms.** Display names, Start menu entries and downloadable assets use Conduit. Internal executable names, installation/data folders, IPC identifiers, update trust and WFP IDs retain their WorkTunnel identity so profiles and recovery remain compatible. The public repository begins with fresh history. Installation and data identifiers retain compatibility with existing installations.

## 2.1 monitoring, recovery and import

`ImportedProxy` is a bounded typed model. The UI reads the selected v2rayN outbound, rejects unsupported options and validates regenerated configs with Conduit's pinned engines before replacing the encrypted profile. The host revalidates all fields and generated engine configs. Import never authorizes arbitrary executable paths, plugin paths, certificate files or arbitrary engine configuration. Hostname endpoints resolve before applying a lock, with an explicitly imported cached IPv4 available when an older lock blocks bootstrap DNS. Source files are not modified. Owner SSH actions are disabled for imported profiles.

`RecoveryPolicy` chooses target, delay and restart budget independently of processes. The controller executes it with cancellation and generation/intent checks. An initial targeted restart escalates to both cores only if verification fails; retries after exhausted cycles run at five-minute intervals and manual Disconnect cancels them. The optional endpoint UDP exception exists only for Shadowsocks and matches the configured server address/port.

`NetworkRecoveryWindow` requires 15 seconds of stable uplink state before verifying the existing engines after network changes. Missing links wait without spending restart budget; unknown link state permits timed verification. The first failed verification targets the adapter and grants 20 seconds for routes to settle. Both grace periods are cancellable by manual Reconnect, Disconnect and disabling automatic recovery. Tests inject the clock, link status, delays and restart outcomes without changing live routes.

`IncidentRecorder` runs in the elevated host. Bounded snapshots/events are redacted before asynchronous, serialized disk writes. It saves the last healthy snapshot at most once per minute, groups incidents for five minutes, and retains 20 report folders under the protected runtime directory. Network facts exclude interface names and addresses; logs include only bounded warning/error lines with credentials, IPs and destination domains scrubbed. The diagnostic exporter includes the latest five incidents. Tests cover cancellation, retention, redaction and damaged diagnostic data; native roaming still requires live validation.

`RouteProbe` asks Windows for best interfaces to two public IPv4 and two public IPv6 addresses. When these pass, `TunnelHealthChecker` also opens an unbound IPv4 HTTPS connection and compares the exit against the expected server, independently of its tunnel-bound probes. A known bypass or failed route lookup skips that unbound request. A missing route result is not a healthy result, except an explicitly absent public IPv6 route. This is sampled verification, not a proof covering every per-app route or destination.

`TunnelDns` sends bounded A queries bound to the TUN address and parses complete replies: transaction and question matching, record boundaries, compression pointers and relevant CNAME/A chains. No Windows DNS fallback is used for health/quality probes. HTTPS handlers bind to the TUN unless explicitly testing ordinary routing. Controller verification requires fresh evidence (less than 60 seconds old), matching network revision and current session. Network changes, engine exit and failed/cancelled verification clear prior evidence; late results cannot restore it. Broker clients expire health and require a recent host snapshot before claiming verification or active filtering.

The host enables sing-box's Clash API on an ephemeral loopback port with a random per-host secret. The secret stays in the restricted runtime config. The host reads bounded `/connections` responses, returns at most 24 aggregated destinations over authenticated IPC, and derives activity from byte-counter deltas. UI polls only while the Connections page is visible and active, every two seconds in Balanced mode or five seconds in Low power mode. The read-only IPC `connections` command grants no API mutation access. Telemetry failures clear the displayed sample rather than inventing connections.

The globe, map geometry and IP geolocation client were removed in 2.3.0. The local live list does not send user destinations to a location provider or save them as browsing history. Normal health checks still contact their configured DNS, HTTPS and STUN services.

The app's single-file bundle is uncompressed to avoid retaining decompressed assemblies in each process's private memory; Setup and update downloads remain compressed. `--release-resource-test <report-path>` runs the offline published checks and writes elapsed time, CPU, private memory and working set. It is a startup/UI test, not an engine or sustained-traffic benchmark. Display sampling runs at one second in Balanced mode, two seconds in Low power mode and five seconds in the background; it stops when hidden/minimized unless Compact view is visible. Profiles are read only on profile refresh, avoiding repeated DPAPI decryption. The wordmark is static and unchanged metric values do not trigger animation.

Validation: release gates include behavioral checks, engine pins, post-obfuscation published checks, offline memory limits, signed installation/repair/uninstall and required native packet fixtures on the disposable runner. The behavioral suite covers import/engine syntax, local v2rayN validation when available, restart selection/budgets, route verdicts, preference migration and an authenticated sing-box API with controlled loopback traffic. Local UI snapshots exercise normal, failure and large-text layouts. Physical IPv6 internet, Windows 11 roaming, sleep and broader application traffic remain additional qualification work; the required IPv6 fixture does not establish those paths.
